# CLAUDE.md — Barraca Hefesto

Contexto rápido para trabajar en este repo. Para estado actual y pendientes, ver `ROADMAP.md`.

## Stack

- **Framework**: [Astro](https://astro.build) v4.16.19
- **Deploy**: [Netlify](https://netlify.com) — autodeploy al hacer push a `main`
- **CSS**: Vanilla CSS con custom properties (sin framework)
- **Fuentes**: todas self-hosted en `src/assets/fonts/` (no Google Fonts) — Inter (cuerpo general, en `fonts/inter/`), Impact (títulos de sección), Carlito (cuerpo de marca — reemplaza a Calibri, ver gotcha de fuente corrupta abajo)
- **Asistente IA**: Netlify Function v2 (`netlify/functions/asistente.js`) + `@anthropic-ai/sdk`, modelo `claude-haiku-4-5-20251001`
- **Repo**: `github.com/nestorhoracio/barraca-hefesto` — la raíz real del proyecto (git, `package.json`, `src/`) es esta carpeta, `hefesto/`

## Estructura (resumen)

- `src/components/` — un `.astro` por sección del one-pager (Header, Servicios, Calculadora, Alquiler, Galeria, Marcas, Nosotros, Contacto, Asistente, Footer)
- `src/layouts/Layout.astro` — head, meta, fonts, dark mode
- `src/pages/index.astro` — página única
- `src/styles/global.css` — tokens de marca (light/dark) + utilidades
- `src/assets/` — fonts, icons (SVG propios), images
- `netlify/functions/asistente.js` — backend del Asistente IA

Árbol completo en [README.md](README.md).

## Convenciones y gotchas técnicos

- **PowerShell**: usar comandos separados, no `&&`.
- **CSS scoped de Astro** no se aplica a elementos creados con `document.createElement()` en un `<script>` de cliente (ej. burbujas del Asistente) — hay que envolver esos selectores en `:global(...)`.
- **Reglas CSS pensadas como globales** (ej. `.section`, `.section-title`) deben vivir en `global.css`, no en el `<style>` de una página o componente. El scoping de Astro le agrega a cada regla un atributo `data-astro-cid-*` que solo matchea elementos del MISMO archivo — si `index.astro` define `.section {...}` pero el `<section class="section">` lo renderiza un componente hijo (`Servicios.astro`, `Alquiler.astro`, etc.), la regla nunca se aplica y el elemento queda con el estilo por defecto, sin avisar de ningún error. Pasó exactamente esto con el padding entre secciones (julio 2026): todas las secciones tenían `padding: 0` porque `.section` estaba en `index.astro` en vez de `global.css`.
- **Íconos**: todos los SVG propios viven en `src/assets/icons/`, se importan con `?raw` y se renderizan con `set:html`, coloreados con `fill:currentColor` / `stroke:currentColor`:
  ```astro
  import AndamioSvg from '../assets/icons/Andamio.svg?raw';
  <div class="card__icon" set:html={AndamioSvg}></div>
  ```
  `lucide-astro` fue eliminado deliberadamente (junio 2026) — no reinstalar, usar este patrón.
- **`npm run dev` no sirve las Netlify Functions** — `/api/asistente` da 404 en local. Para probar el Asistente IA local hace falta [`netlify dev`](https://cli.netlify.com/) (netlify-cli).
- **`netlify dev` recarga el módulo de cada function en cada request** — cualquier estado en memoria a nivel de módulo (contadores, caches, un `Map`) nunca se acumula entre requests en local, aunque el código esté bien escrito. Confirmado el 2026-07-25 con un `console.log` de diagnóstico en un rate limiter casero que probé y descarté: 17 requests seguidos mostraron `mapSize=1` todas las veces. No es un bug — es que el simulador local prioriza hot-reload de código por sobre imitar la reutilización de contenedor "warm" que sí ocurre en producción. Este tipo de lógica solo se puede validar de verdad probando después de un deploy real.
- **Panel de DNS de nic.com.uy (modo "Alojado")**: la vista básica solo muestra "Web" (una IP) y "Mail" (MX ya configurado — no tocar, es el correo real del cliente vía Google Workspace) — para cargar registros A/CNAME adicionales hay que abrir "Configuración avanzada" → "Agregar registro". El formulario de CNAME no usa los campos "Nombre"/"Valor" sino **"Alias"** (nombre del registro) y **"Nombre real"** (destino), y ambos necesitan un punto final (`.`) para indicar FQDN — sin el punto, el panel concatena `.hefesto.com.uy` al valor cargado (hay una vista previa "Resultado" en el propio formulario para verificarlo antes de guardar). El link **"Delegar"** cambia el dominio a delegación por nameservers externos — no clickearlo, rompería el modo "Alojado" actual y el correo de Google Workspace. Confirmado el 27/7/2026 conectando `hefesto.com.uy` (detalle completo en `ROADMAP.md`).
- **Proyecto vinculado a Netlify vía `netlify link`** (site id `8aeb14e9-bf61-492e-a082-629a370c51b3`, cuenta `nesthora@gmail.com`) — permite usar `netlify api <método>` (ej. `updateSite`, `getSite`) para gestionar el sitio sin pasar por el panel web. No hace falta repetir `netlify link` en sesiones futuras salvo que se pierda el vínculo local (`.netlify/state.json`).
- **Rate limiting de `/api/asistente`**: se usa el rate limiting nativo de Netlify (campo `rateLimit` en el `config` exportado de `asistente.js`, no un `Map` en memoria) — funciona en cualquier plan, se aplica a nivel de plataforma antes de que corra la función, y por eso tampoco se puede probar con `netlify dev` (Netlify solo lo valida/activa en el post-processing del deploy). `windowSize` tiene un máximo de 180 segundos impuesto por Netlify. Para cambiar el límite, editar ese mismo objeto — no hace falta tocar el cuerpo de la función.
- **Asistente IA**: catálogo cerrado de 4 tipos de chapa (Ondulada/Trapezoidal Aluminizada × Calibre 26/30) y de caños/perfiles de hierro (cuadrado, rectangular, redondo, Perfil C, ángulos, planchuela lisa/perforada, varilla lisa/tratada — todo x barra de 6m, sin fraccionar) — no debe ofrecer ni inventar otras variantes. Caños y perfiles nunca lleva precio, ni aproximado (a diferencia del resto de las categorías) — el hierro cambia de precio muy seguido.
- **Endpoint `/api/asistente` — validación server-side** (2026-07-25): chequea `Origin`/`Referer` contra un allowlist (403 si no matchea), valida forma y longitud de `mensajes` (400 si no cumple, corta el historial a los últimos 20 y cada mensaje a 2000 caracteres), y el frontend (`Asistente.astro`) escapa el HTML del bloque de RESUMEN antes de insertarlo con `innerHTML` (antes había un XSS acotado ahí). No sacar estos chequeos sin agregar un reemplazo — el endpoint queda expuesto públicamente en `hefesto.com.uy`.
- **Regex de extracción del mensaje WhatsApp** en el cliente: `/MENSAJE_WA:\s*([\s\S]+)/` (greedy, captura hasta fin de string). Si falla, se muestra error al usuario — no hay fallback que mande el último mensaje tal cual.
- **`-webkit-text-stroke` con valores sub-píxel no se afina de forma confiable**: bajar el ancho de `1px` a `0.4px`, `0.08px` o incluso `0.01px` (probado en `.section-title`, `global.css`, 2026-07-25) no tuvo ningún efecto visual perceptible — los navegadores redondean el stroke al renderizar en vez de interpolarlo, así que un número más chico no garantiza un trazo más fino. Para atenuar un contorno de texto de forma confiable, bajar la opacidad del color con `color-mix(in srgb, var(--color) X%, transparent)` en vez de (o además de) bajar el ancho — ej. `-webkit-text-stroke: 0.5px color-mix(in srgb, var(--color-brand) 22%, transparent)`.
- **`@astrojs/sitemap` pinneado a `3.2.1` exacto (sin `^`)** en `package.json` — versiones más nuevas (3.3.0+) se compilan contra Astro 5/6 y usan el hook de integración `astro:routes:resolved`, que no dispara igual en Astro 4.16 (versión actual del proyecto): rompe el build en `astro:build:done` con `Cannot read properties of undefined (reading 'reduce')`. No correr `npm update`/`npm install @astrojs/sitemap` sin fijar la versión, salvo que se suba Astro a la vez.
- **No mezclar `aspect-ratio` + `max-height` + `object-fit` en un elemento reemplazado (`<img>`/`<Image>`)**: en `Nosotros.astro` esa combinación en el mismo `<img>` causó que en mobile (ancho angosto) el navegador ignorara el `aspect-ratio` calculado (más chico) y forzara la altura hasta el `max-height` del media query, angostando la caja y haciendo que `object-fit:cover` recortara los costados de la foto — un `max-height` no debería nunca *aumentar* una altura ya menor, pero en este caso sí. Confirmado con medición real en Playwright (viewport mobile), no solo por inspección visual. Patrón correcto: poner `aspect-ratio`/`max-height`/`width:100%` en el `<div>` contenedor (no reemplazado, con `overflow:hidden`) y dejar el `<img>` solo con `width:100%; height:100%; object-fit:cover`.
- **`astro:assets` (`<Image>`) vs `<img>` plano**: usar `<Image>` para fotos importadas desde `src/assets/images/` (ya migrado en `Nosotros.astro`, `Galeria.astro`). **Excepción**: `Marcas.astro` usa logos en `public/marcas/` referenciados por string (`/marcas/x.png`) — `astro:assets` no optimiza archivos de `public/` (no pasan por el pipeline de build), así que ahí el fix de CLS es `width`/`height` explícitos por logo en vez de migrar a `<Image>`. No mover esos archivos a `src/` sin necesidad — son assets de marca provistos por terceros.
- **`border-radius` grande no tiene ningún efecto visible en elementos chicos tipo píldora/badge/tag**: el navegador clampea (limita) el radio efectivo a la mitad de la altura de la caja — en una caja de ~36-40px de alto (badges del hero, tags de `.tamano` en Alquiler), pedir `border-radius: 24px` (`--radius-lg`) rinde exactamente igual que `999px`, porque ambos superan la mitad de la altura y quedan clampeados al mismo valor (una píldora completa). Confirmado el 26/7/2026 intentando "normalizar" esos elementos con `--radius-lg` sin cambio visual aparente. Para que un elemento chico se vea con esquinas redondeadas reales (no píldora), el radio pedido tiene que ser claramente menor a la mitad de su altura — en este proyecto se resolvió usando `--radius-sm` (10px) en esos casos.
- **Escala de `--radius-sm/md/lg`** (`global.css`) calibrada el 26/7/2026 al redondeo real del logo: se midió el PNG del isotipo a nivel de píxel (decodificando manualmente con `zlib`/`struct` de Python, sin Pillow disponible) y el radio de la forma es ~28.8% del ancho del cuadrado del isotipo, consistente en las dos variantes del logo y ambas esquinas — valor bastante más alto que la escala anterior (6/10/16px). Los tres chips de ícono con fondo (`.card__icon`, `.alq-card__icon`, `.info-item__icon`) usan ese 28.8% de forma literal según su tamaño real (14px/15px/12px) en vez del token genérico, por precisión.
- **Fuentes locales corruptas — `calibri.woff2`/`calibrib.woff2` reemplazadas por Carlito (28/7/2026)**: el archivo `calibri.woff2` (regular) le faltaba el glyph de la "A" mayúscula, y `calibrib.woff2` (negrita) además le faltaba "P"/"p" — el glyph "existía" (el navegador no hacía fallback a otra fuente, no era un problema de CSS ni de cómo se usaban) pero el contorno estaba vacío. Esto hacía que en TODO el sitio (Calibri es la fuente de `body` por defecto) desaparecieran letras sueltas — ej. "Todo para tu obra" se veía "Todo ara tu obra", "PASO" se veía "P SO". Confirmado como bug preexistente en producción (no causado por la sesión que lo encontró) reproduciéndolo con `git stash` sobre el código sin tocar, y aislado con una prueba mínima (HTML solo con el `.woff2` en cuestión y el alfabeto completo, fuera del sitio). Se reemplazó por **Carlito** (`src/assets/fonts/carlito.woff2`/`carlitob.woff2`, descargado de Google Fonts y auto-hospedado igual que el resto), un font open-source (SIL OFL) diseñado específicamente como sustituto métricamente idéntico a Calibri — mismos anchos de carácter, cero reflow, y evita además la ambigüedad de licencia de embeber Calibri (propietario de Microsoft) como web font en un sitio público. La variable se renombró `--font-calibri` → `--font-carlito` en `global.css` (únicas dos referencias en todo el código: la declaración y `body { font-family: var(--font-carlito) }`) para que el nombre no mienta sobre qué fuente es. Antes de reemplazar cualquier fuente local, conviene verificarla aislada (HTML mínimo con el alfabeto completo A-Z/a-z/0-9 + tildes, sin el resto del sitio) — así se detectó y confirmó este bug.

## Rendimiento y SEO (mobile-first)

- **SSG obligatorio**: Astro debe mantenerse en modo estático (sin `output: 'server'` en `astro.config.mjs`) — todo el contenido semántico principal se renderiza en build, sin depender de JS en cliente para que Googlebot lo indexe. Motivo puntual: Googlebot indexa en dos fases (HTML crudo primero, renderizado JS después, con cola y demora) — depender del CSR arriesga contenido no indexado o indexado tarde.
- **TBT**: JS de cliente mínimo, vanilla y encapsulado por componente (mismo patrón que ya usan el Asistente y el toggle de dark mode) — no sumar librerías pesadas de interactividad.
- **LCP**: imágenes de producción en WebP/AVIF, no PNG/JPEG pesados en elementos críticos (hero, logo). Preferir `astro:assets` (`<Image>`/`<Picture>`) sobre `<img src={x.src}>` plano para optimización automática.
  - `Nosotros.astro`, `Galeria.astro`, `Header.astro`, `Footer.astro` y `Asistente.astro` ya usan `astro:assets` (`<Image>` o `getImage()`, conversión automática a WebP). El hero (`banner.jpg` en `index.astro`) usa `getImage()` en vez de `<Image>` porque se renderiza como `background-image` inline, no `<img>` — Astro no lo optimiza automáticamente en ese patrón, hay que llamar `getImage()` a mano en el frontmatter y usar `.src` en el `style` (28/7/2026: 102KB→40KB). Se agregó `<link rel="preload" as="image" fetchpriority="high">` en `Layout.astro` (prop `preloadImage`, pasada desde `index.astro`) para que el hero se descubra sin esperar el parseo del CSS.
- **CLS**: todo `<img>` debe declarar `width`/`height` explícitos para reservar espacio y evitar saltos visuales.
  - Resuelto en todos los componentes: `Nosotros.astro`, `Galeria.astro`, `Header.astro`, `Footer.astro` y `Asistente.astro` vía `astro:assets` (que los infiere), y `Marcas.astro` con `width`/`height` explícitos por logo (no pasa por `astro:assets` porque son archivos de `public/`, ver gotcha de logos de marcas abajo).
- **Fuentes self-hosted, no Google Fonts (28/7/2026)**: Inter también se auto-hospeda ahora (`src/assets/fonts/inter/`, 5 pesos 400/500/600/700/900, mismo patrón `@font-face` + `font-display: swap` que Impact/Carlito) — antes se cargaba con `<link rel="preconnect">` + `<link rel="stylesheet">` a `fonts.googleapis.com` en `Layout.astro`, bloqueando el render de toda la página por una fuente que ni se usa arriba del fold (Inter solo aparece en `Asistente.astro`, un widget cerrado por defecto). Sin preload para Inter — no es crítica para el primer render, igual que Impact/Carlito.
- **CSS bundleado en un solo archivo — render-blocking aceptado a propósito**: Astro junta `global.css` + el `<style>` scoped de cada componente en un único `link rel="stylesheet"` por página (~5-6KB minificado hoy). PageSpeed lo marca como "solicitud que bloquea el renderizado" (~1350ms estimados, confirmado 28/7/2026 en producción), pero partirlo en crítico/no-crítico no se justifica en este proyecto: es un one-pager (todo el CSS se necesita para pintar la página completa igual, no hay rutas con CSS no usado) y el archivo ya es chico. No perseguir ese punto salvo que el sitio crezca a múltiples páginas con CSS realmente no compartido.
- **Cache headers (`netlify.toml`, 28/7/2026)**: se agregó `[[headers]]` — `/_astro/*` (JS/CSS/imágenes/fuentes hasheados por Astro en cada build) con `Cache-Control: public, max-age=31536000, immutable`; assets de `public/` sin hash en el nombre (`/marcas/*`, `/favicon.png`, `/apple-touch-icon.png`) con `max-age=604800` (una semana, sin `immutable` — si se reemplaza el archivo sin cambiar el nombre no debe quedar cacheado un año). Solo se puede confirmar el header real después de un deploy a Netlify, no con build/`netlify dev` local.
- **Favicon a tamaño real (28/7/2026)**: `public/favicon.png` reusaba el PNG completo del logo (57KB) sin redimensionar, y `apple-touch-icon` apuntaba al mismo archivo. Se regeneraron una sola vez con un script puntual de Node + `sharp` (ya presente como dependencia transitiva de Astro, no se instaló nada nuevo) — mismo criterio que el recorte del isotipo "H" documentado en `ROADMAP.md` (herramienta puntual, no pipeline de build): `favicon.png` a 48×48 (57KB→1.6KB) y `apple-touch-icon.png` nuevo a 180×180 (4.8KB). Si el logo cambia, hay que volver a correr el resize a mano — no está automatizado en el build.
- **SEO técnico ya implementado** (`Layout.astro` / `astro.config.mjs`): canonical dinámico vía `Astro.site`, JSON-LD `HardwareStore`/`LocalBusiness` (dirección, geo, horarios, redes, `description` — hardcodeado ahí mismo, mismo patrón que `Contacto.astro`, sin archivo de datos separado), `og:image`/`twitter:image` en URL absoluta, sitemap automático (`@astrojs/sitemap`, ver gotcha de versión arriba), `public/robots.txt`. Todo deriva de `Astro.site`, así que la migración de dominio (ver `ROADMAP.md`) solo requiere cambiar ese valor — **excepto `robots.txt`**, que tiene la URL del sitemap hardcodeada a mano.
- **SEO técnico ≠ SEO de rankeo.** PageSpeed en 100/100 de SEO solo valida checklist técnico (meta tags, crawlability, mobile-friendly) — no garantiza aparecer en resultados para búsquedas comerciales. Si el sitio no rankea para términos como "Barraca Paso de los Toros" o "venta de chapas" y el técnico ya está bien, antes de tocar código revisar: 1) cuánto hace que se migró/pidió indexar el dominio (Google tarda días-semanas incluso con todo bien configurado, más para dominio nuevo sin backlinks); 2) si la búsqueda depende del "3-pack" de mapas, que se resuelve con el Google Business Profile (categorías, reseñas, fotos), no con el sitio web; 3) si las frases exactas buscadas aparecen como texto visible real en la página (no alcanza con que estén en el `title`/meta description). Confirmado el 29/7: con SEO técnico en 100, la causa de no aparecer para esos términos era (a) dominio migrado hacía 2 días, (b) "perfiles" y "venta de chapas"/"venta de perfiles" no existían como texto visible en ningún componente — se resolvió reforzando copy natural en `Servicios.astro`, `Alquiler.astro`, `Footer.astro`, `Galeria.astro` y el `description` del JSON-LD, sin tocar nada técnico (ya estaba bien).
- **Link estable a la ficha de Google Maps desde el CID del iframe embebido**: `Contacto.astro` tiene un `<iframe>` de Google Maps cuya URL contiene un identificador `!1s0x...%3A0x...!2sBarraca%20Hefesto` (formato `ftid`, no es el `place_id` de la Places API). La segunda mitad hex (después de los dos puntos) es el CID del negocio — convertido a decimal (`python3 -c "print(int('4b6b12fd293ec14f', 16))"` → `5434458253880639823`), arma un link directo y estable a la ficha: `https://www.google.com/maps?cid=5434458253880639823` (usado en `sameAs` del JSON-LD de `Layout.astro`). Útil para vincular sitio↔Google Business Profile sin depender de tener acceso a la cuenta de Google del negocio ni de la Places API.
- **Video de fondo del hero — solo desktop, en ambos temas (1/8/2026, ajustado el mismo día)**: el `<video>` de `index.astro` se renderiza SIN `src` ni `<source>` en el HTML (solo `poster`) — un script de cliente le asigna `src` recién si `matchMedia('(min-width: 769px)')` + no `prefers-reduced-motion` se cumplen, evaluado después del evento `load` de la página. Esto es a propósito para que mobile no descargue ni un byte del video (poner `display:none` en CSS no alcanza — la mayoría de navegadores igual descargan un `<video>` con `src`/`<source>` en el HTML inicial). Primera versión (mismo día) restringía el video también a tema claro — se sacó esa condición a pedido de NH tras ver capturas en producción: el video se reproduce igual en tema oscuro, con el overlay oscuro existente encima (mismo criterio que ya tenía la imagen estática antes). El `.mp4` vive en `public/videos/` (no puede pasar por `astro:assets`, Astro no procesa video) con el nombre versionado a mano (`hero-loop-light-v1.mp4`) porque `public/` no hashea — si llega una v2, sube como archivo nuevo y se actualiza la constante `VIDEO_SRC` en el script, no se sobreescribe el mismo nombre (que quedaría cacheado `immutable` un año por el header de `netlify.toml`).
- **No hardcodear texto en MAYÚSCULAS en el contenido** — si el diseño pide mayúsculas visuales (ej. `hero__sub` en `index.astro`), escribir el string en case normal y aplicar `text-transform: uppercase` en el CSS del componente. Un string literal en caps se filtra tal cual a cualquier reuso (meta description, `og:description`, JSON-LD), y en un `<meta>` no hay CSS que lo "arregle" — se ve gritado en el snippet de Google. Corregido el 29/7 en `Layout.astro` (meta description) e `index.astro` (`hero__sub` + regla `text-transform:uppercase` agregada a esa clase).

## Componentes Astro — arquitectura

- Modularizar con `interface Props` tipada cuando el componente reciba datos variables (hoy solo `Layout.astro` la usa — nuevos componentes o refactors que acepten props deben declararla).
- CSS scoped por componente para evitar fugas de estilo (ver gotcha de reglas globales arriba).
- Renderizado condicional limpio (`{condicion && <Elemento />}`) para elementos opcionales — ej. futuros badges de certificaciones o marcas.
